# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Passaggio is an iPhone app (iOS 26+, SwiftUI + SwiftData) that turns recorded singing lessons into key points, recurring-feedback insights, practice routines and piano practice tracks. See `README.md` for the user-facing feature list and install steps, and `VERIFY.md` for the manual on-device checklist.

## Commands

`Passaggio.xcodeproj` is generated by XcodeGen from `project.yml` and is git-ignored. Edit `project.yml`, never the project file, then run `make project`. Every `make` target that builds does this for you.

```sh
make bootstrap TEAM_ID=…   # first time: writes Config/Local.xcconfig, generates the project, runs doctor
make test-core             # PassaggioCore tests (swift test); no simulator needed
make test                  # core tests, then app tests on the simulator (override with SIM_DEST=...)
make build-sim             # build the app for the simulator
make build-device TEAM_ID=…
make samples               # regenerate Fixtures/ (needs ffmpeg)
OPENAI_API_KEY=… ANTHROPIC_API_KEY=… make smoke   # one real, cheap call to each API
```

Run a single test (both suites use Swift Testing, not XCTest):

```sh
cd Packages/PassaggioCore && swift test --filter NoteTests            # a suite, by struct name
cd Packages/PassaggioCore && swift test --filter "NoteTests/nameRoundTripsAcrossPianoRange"  # one test
xcodebuild test -project Passaggio.xcodeproj -scheme Passaggio \
  -destination 'platform=iOS Simulator,name=iPhone 16 Pro' -derivedDataPath build/DerivedData \
  -only-testing:PassaggioTests/PassaggioAppTests/builtInPresetsSeedOnce
```

## Architecture

There are two layers, and the split is deliberate:

- **`Packages/PassaggioCore`** is plain Foundation with no SwiftUI, SwiftData or AVFoundation, so `swift test` runs anywhere. It holds all logic that can be tested without Apple frameworks: transcription chunk planning and merging of diarized chunks (`Transcription/`), the OpenAI and Anthropic `LLMProvider` implementations and response parsing (`LLM/`), prompt building and key-point/topic extraction (`Notes/FeedbackAnalyst.swift`, `RecurrenceMatcher`), note and exercise math (`Music/`), routine weighting (`Routine/RoutinePlanner`), and the tar backup format (`Archive/`). Network calls go through the `HTTPClient` protocol. Tests replay recorded JSON from `Tests/PassaggioCoreTests/Fixtures/` through `StubHTTPClient` and `StubLLM` in `TestSupport.swift`, and never hit live APIs. Put new pure logic here and test it here.
- **`Passaggio/`** is the iOS app. `Model/Models.swift` holds every SwiftData `@Model`, and they're registered in `PassaggioSchema.models`. `Services/` adapts core logic to Apple frameworks. `Features/<Area>/` holds the SwiftUI screens. `PassaggioTests/` covers only what needs Apple frameworks: the SwiftData backup round trip, audio rendering and the Keychain.

How the app fits together:

- `PassaggioApp` creates `AppSettings` (UserDefaults preferences, plus factories that build the transcription client and the selected `LLMProvider` with keys from `KeychainStore`), `PlayerController` (the single shared audio player) and `LessonProcessor`. It injects them with `.environment(...)`, so views read them with `@Environment(Type.self)`.
- `LessonProcessor` runs the pipeline for a lesson: `AudioAnalysis` → `ChunkPlanner` → OpenAI diarized transcription (with the teacher and student voice samples as known speakers) → `FeedbackAnalyst` → topics. It tracks per-lesson `Task`s and progress, and moves `Lesson.status` through `ProcessingStatus`. If no segment is labelled as the teacher, it stops at `.needsSpeakers` for the user to choose.
- Only teacher speech goes to the LLM, and the prompts must only organise and quote the teacher, never add advice of their own (`FeedbackAnalyst.principles`). Keep this rule when you edit prompts.
- Audio files live in `FileStore` (Application Support for recordings and voice samples; Caches for rendered tracks and scratch files). SwiftData models store only file names.
- Exercise tracks are rendered offline to WAV by `ExerciseRenderer` (`AVAudioEngine` manual rendering driving `AVAudioUnitSampler` with the bundled `UprightPianoKW.sf2`), then cached by a hash of their parameters. They aren't sequenced live.
- `BackupService` writes `data.json` (`BackupPayload`, made of hand-written DTOs that mirror each model) plus `recordings/` and `references/` into a tar file. **When you add or change a persisted model property, update the matching DTO, its export and its restore code, and the round-trip test in `PassaggioTests`.** Bump `BackupService.formatVersion` if old backups can no longer be read.

## Conventions

- Concurrency: the app target is main-actor by default (`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, approachable concurrency) in Swift 5 mode with complete strict-concurrency checking. Mark audio, rendering and archive work `@concurrent`, and mark plain value types and enums that are used off the main actor `nonisolated`. PassaggioCore is a Swift 6 package.
- SwiftData enums are stored as raw `String`s with typed computed accessors, which keeps `#Predicate` and the backup JSON simple. Follow the same pattern for new enum-valued properties.
- SwiftUI previews use `#Preview(traits: .sampleData)` from `Features/Shared/SampleData.swift` (DEBUG only).
- `Passaggio/Info.plist` is hand-maintained and contains explanatory comments. Xcode sometimes rewrites it (sorting keys, stripping comments, removing keys). Don't commit a rewrite like that; restore the commented version.
- The bundle ID in `Config/Base.xcconfig` must never change: free-provisioning reinstalls rely on it to keep user data. The Team ID goes in the git-ignored `Config/Local.xcconfig`.
- No entitlements file on purpose: Personal Team signing can't use iCloud, App Groups or push.

## Design

- Follow Apple's Human Interface Guidelines. The app should feel like one of Apple's own apps.
- Build with standard SwiftUI components (NavigationStack, List, Form, sheets, toolbars). Create a custom component only when no standard one fits.
- Use the system font with semantic text styles (.largeTitle, .headline, .body, .caption) so Dynamic Type works.
- Use semantic system colors so light and dark mode both work.
- Use one accent color throughout, for primary actions and the active playback state.
- I use the practice and playback screens while singing, often with the phone on a stand, so make those controls large, high-contrast, and reachable with one thumb.
- Label every control for VoiceOver.
